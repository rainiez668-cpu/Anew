# Anew 产品需求文档

**Product Requirements Document · PRD v2.0**

**产品名称：** Anew
**产品类型：** 移动优先的每日计划 Web 应用
**项目性质：** 个人独立设计与 AI 辅助开发项目
**当前阶段：** 可运行 MVP / 原型验证阶段
**核心定位：** 面向启动困难人群的低负担每日计划工具

---

## 01 / 产品摘要

### 1.1 产品概述

Anew 是一款移动优先、面向任务启动困难人群的每日计划应用，帮助用户将一天的任务管理过程转化为一个轻量、可持续的行动循环：

**选择（Pick）→ 专注（Focus）→ 完成（Done）→ 复盘（Review）**

不同于强调任务数量、优先级排序与完成效率的传统待办工具，Anew 关注的是用户在真正开始行动之前所面临的决策负担。

产品通过一次呈现一张候选任务卡片、简单的二元选择、单任务专注与非惩罚性的完成反馈，减少用户在规划阶段反复比较和权衡的需求。

在一天结束时，用户可以通过简短的复盘整理想法，并将其转化为下一天的候选任务，让每日计划形成连续但不具有强制性的循环。

**Anew 的目标不是帮助用户管理更多任务，而是降低从决定做什么到真正开始行动之间的阻力。**

### 1.2 产品价值主张

Anew 希望提供一种不同于传统任务管理工具的使用体验：

- **更容易选择：** 不要求用户先浏览完整清单并排列优先级，而是逐项判断任务是否适合今天。
- **更容易开始：** 在执行阶段聚焦当前任务，减少切换与反复选择。
- **更容易继续：** 允许跳过、暂停或未完成任务，不使用惩罚性提醒和连续打卡机制。
- **更容易回顾：** 通过简短复盘帮助用户整理进展，并为下一次行动提供起点。

产品并不追求消除所有决策，而是尽可能降低开始行动前不必要的认知负担。

### 1.3 当前版本状态

Anew 已形成覆盖任务选择、专注、完成和复盘的可运行 MVP，并建立 Today、Focus、Review 三个主要页面。

当前公开 Demo 中，AI 任务规划与复盘对话采用预设模拟回复，不需要用户配置 API 密钥，也不会产生真实模型调用费用。项目代码已包含 `/api/ai-plan` 与 `/api/review-chat` 接口，以及模拟（Mock）、OpenAI 和 Anthropic 三种模型服务适配能力。

代码具备真实模型接入基础，但公开 Demo 未启用真实 AI，真实模型的完整集成效果仍需通过部署配置与测试验证。

## 02 / 目标用户与使用场景

### 2.1 主要目标用户

经常面临任务启动困难、时间感知偏差或任务积压带来的心理负担的人群。Anew 不要求用户具有正式医学诊断，也不提供诊断或治疗功能。

这类用户可能表现出以下使用困难：

- 能够意识到需要完成什么，却难以决定先做哪一件事。
- 面对较长的任务清单时，需要反复比较优先级和时间成本。
- 容易因为任务尚未完成而产生压力，并逐渐回避打开任务工具。
- 对剩余时间、任务耗时或行动进展缺乏清晰感知。
- 在中断后需要重新进入任务时，容易再次陷入选择与启动困难。

### 2.2 次要目标用户

不一定存在持续性任务启动困难，但认为传统待办应用过于复杂、信息密度过高或具有压力感的普通用户。

### 2.3 典型使用场景

**场景 A：开始一天前** — 用户积累了多项待办，不知从哪件开始。打开 Anew 后逐张判断候选任务是否适合今天，逐步形成当日计划。

**场景 B：准备开始任务时** — 用户已选好今天要做的事，但容易犹豫。进入 Focus（专注）后界面聚焦当前任务，提供行动步骤和可选计时器。

**场景 C：某项任务暂时不适合今天** — 用户选择「今天不做（Not today）」将任务暂时排除，不必标记为失败。

**场景 D：一天结束时** — 用户希望回顾但不愿面对完成率报表。Anew 提供简短对话式复盘，并可将反思转化为明日候选任务。

### 2.4 非目标用户

- 需要管理多个长期项目及复杂依赖关系的用户。
- 需要多人协作、任务分配与共享进度的团队。
- 依赖精确日历排程与时间冲突管理的用户。
- 需要详细绩效报表与复杂数据分析的用户。

## 03 / 核心问题与设计假设

### 3.1 核心问题

传统待办工具假设用户愿意在开始工作之前完成一套决策流程：通览全部任务 → 比较优先级 → 估算耗时 → 判断精力匹配 → 排序 → 开始执行。对存在启动困难的用户，前面的比较和排序本身就可能消耗大量注意力。

用户虽然成功记录了任务，却仍然无法迈出开始行动的第一步。

Anew 关注的问题不是如何进一步优化任务排序，而是：

**如何减少「排列任务」这一动作本身的负担，让用户更容易开始第一件事？**

### 3.2 设计切入点

Anew 将任务规划从「并列浏览与排序」转向「渐进式选择」。用户不需要一次处理全部候选任务，而是逐个回答一个相对简单的问题：

**这件事，我今天要做吗？**

### 3.3 核心设计假设

相比传统的任务并列展示与提前排序模式，**「逐项选择 + 单任务聚焦」**的渐进式选择方式，有望降低任务启动前的决策负担，帮助存在启动困难的用户更快开始第一项任务。

这一假设包含两个需要分别验证的方向：

1. **决策体验：** 渐进式选择是否让用户觉得任务规划更轻松、更容易理解。
2. **行动效率：** 渐进式选择是否能够缩短从进入规划流程到真正开始任务的时间。

二者不一定同时成立。用户可能认为逐张选择更轻松，但实际操作时间并未缩短。因此，不能仅通过界面的主观偏好判断设计是否有效。

### 3.4 假设来源

该假设来源于对传统待办工具使用体验的个人观察：任务可以被记录下来，但面对完整清单时仍然很难决定先开始什么。个人体验可作为设计问题的起点，但不能替代针对目标用户的正式研究。

### 3.5 当前验证状态

已完成 5 人可用性测试，核心交互对目标人群具有首次使用可理解性。量化验证受限于无埋点，尚无法证明 Anew 在任务启动时间或决策负担方面显著优于传统待办清单。核心假设仍需通过真实用户研究和对照测试进一步验证。

### 3.6 潜在反证信号

以下情况可能意味着当前设计假设不成立，或仅适用于部分用户：

- 用户认为逐张选择比直接浏览完整清单更慢。
- 用户频繁希望查看全部任务，再决定今天要做什么。
- 用户完成了大量滑动操作，却没有更快开始行动。
- 任务跳过率较高，但后续实际完成情况没有改善。
- 用户无法理解任务跳过后的去向，反而增加操作不确定性。
- 用户在 Focus 页面仍然需要反复切换任务，单任务展示未能减少启动阻力。

### 3.7 产品非目标

| 不纳入当前产品方向 | 设计原因 |
|---|---|
| 多用户协作与任务分享 | 核心目标是降低个人任务启动成本，协作可能引入额外协调负担 |
| 复杂的长期项目管理 | 大规模任务组织容易重新形成需要通览和排序的清单 |
| 连续打卡与断签惩罚 | 避免将某一天的中断转化为长期使用压力 |
| 默认推送通知与强制提醒 | 优先探索由用户主动控制的任务启动过程 |
| 面向绩效的完成率报表 | 避免把反思体验转化为持续性的效率评价 |

以上属于当前明确的产品边界，不应简单理解为尚未开发的功能清单。

## 04 / 产品设计原则

1. **一次只处理一件事** — 规划时一次展示一张候选卡片，执行时聚焦一个当前任务。
2. **降低不必要的决策负担** — 减少开始行动前必须完成的排序、分类和优先级判断；不为简化而简化，优先保留对当前行动真正必要的信息。
3. **使用平和、无惩罚性的反馈** — 避免使用失败、落后、断签等表达制造压力。允许用户跳过任务、调整计划或在中断后重新开始。
4. **让下一步与操作结果清晰可见** — 用户不仅应知道当前可以做什么，也应理解操作之后会发生什么。
5. **支持不同的时间感知与专注节奏** — 通过可选计时器、可选任务步骤和适当反馈帮助用户感知当前行动。时间辅助与步骤拆分不应成为必须完成的额外任务。
6. **完成有反馈，但不喧闹** — 避免夸张动画、竞争性分数或过度强调效率的反馈机制。
7. **数据本地优先，并允许用户迁移** — 用户无需注册即可使用核心功能。任务和复盘数据默认保存在本地，支持主动备份、恢复与重置。
8. **AI 是可选增强，而非核心依赖** — 即使没有真实 AI 服务，用户仍应能够完成核心流程。AI 用于帮助整理、表达和生成建议，不替代用户决定应该做什么。
9. **可理解性与可访问性优先于视觉简化** — 减少视觉元素不应造成操作含义不清、文字对比度不足或辅助技术无法使用。

> 当设计原则出现冲突时，按编号靠前者优先。

## 05 / 信息架构与核心交互

### 5.1 产品信息架构

Anew 使用三个主要导航页面：**Today / Focus / Review**，对应规划、执行和回顾。「完成（Done）」不作为独立页面，而是任务执行后的状态变化。

### 5.2 Today：选择与今日计划

**页面目标：** 帮助用户在不需要通览完整任务列表的情况下，确定今天准备做什么。

主要内容：逐张展示候选任务的滑动规划器、当日已选择任务、今日大事（One Big Thing）、每日基础事项（Daily Basics）。

#### 候选任务选择

默认一次展示一张候选任务卡片。用户可以通过以下方式做出决定：

- **右滑 / 加入今天（Keep today）：** 将任务加入今日计划。
- **左滑 / 今天不做（Not today）：** 暂时不将该任务纳入今天。

需要同时提供等效按钮操作，避免用户必须通过滑动手势完成决策。

#### 任务跳过原则

「今天不做（Not today）」表示当前不选择该任务，不表示任务失败或永久删除。跳过的任务在日切后重新进入候选范围，不以惩罚性标签呈现。

仍需完善的是状态可理解性：用户需要知道「今天不做」不代表删除，应明确任务何时可能再次出现，不应让用户因任务暂时消失而误以为数据丢失。

#### 今日大事（One Big Thing）

用户可以在今日任务中标记一项相对重要的任务，形成明确的行动焦点。产品设计约束为至多一个有效标记——标记新的会自动取消旧的。

#### 每日基础事项（Daily Basics）

用于记录需要经常重复、但不适合每天重新创建的基础事项。清单本身持续保留，每日勾选状态在日切时重置，完成状态不转化为连续打卡惩罚。

#### 快速添加（Quick Add）

用户可以为今日计划主动创建任务，而不必等待候选任务被推送。快速添加会为任务生成一组默认行动步骤。

**行动步骤为可选内容，而非必填字段**：用户应能够自行添加、编辑或删除步骤，或在不需要步骤说明时直接留空（依据可用性测试发现 P05——"这个步骤是自带的吗？我想自己写的话，在哪里改？"）。不应让自动生成的步骤被误认为固定模板，从而增加理解成本。

### 5.3 Focus：单任务专注

**页面目标：** 减少用户在执行阶段反复浏览和切换任务的需要。

主要内容：当前聚焦任务、可执行的行动步骤、可选计时器（15/25/45 分钟 + 自定义）、任务完成操作、温和重入提示。

**单任务展示：** Focus 以一个当前任务作为主要视觉焦点，避免完整任务列表持续占据注意力。产品不试图完全消除「下一件做什么」的问题，而是减少用户在每次开始行动前重新进行复杂排序的需求。

**行动步骤：** 步骤为可选内容，支持用户添加、编辑与删除，不成为开始任务的前提。任务可以没有步骤，也可以由 AI 建议一批步骤后由用户自由修改或采纳。

**可选计时器：** 计时器作为可选辅助工具，不是任务开始或完成的前置条件。计时结束不自动意味着任务失败。

**温和重入：** 允许用户在专注中断后重新进入任务而不产生失败提示。当前版本中，同一任务持续超过 5 分钟会出现一次温和提示，用户可关闭，且关闭后当天不再出现。

### 5.4 完成状态（Done）

完成是任务状态，不是独立页面。用户可以在 Today 或 Focus 中标记任务完成。完成操作提供明确反馈，不使用惩罚性红绿状态对比、完成率排名或「进度落后」提示。

### 5.5 Review：每日复盘

**页面目标：** 通过轻量反思帮助用户整理当日体验，并为下一次行动提供起点。

主要内容：对话式复盘、可选语音输入、AI 辅助生成建议、将复盘内容转化为明日候选任务。

复盘不以完成率或未完成数量为主要评价标准。用户即使没有完成任何任务，也应能够进行反思。

**AI 辅助复盘：** 公开 Demo 使用预设模拟回复。真实模型模式需自部署并配置密钥，效果需实际验证。

**可选语音输入：** 依赖浏览器支持（Chrome、Edge、Safari 均可，需 HTTPS 环境），不支持时界面给出提示。中文识别效果取决于浏览器能力。

### 5.6 核心操作与状态转换

| 用户操作 | 产品预期 |
|---|---|
| 将候选任务加入今天 | 任务进入今日计划 |
| 选择「今天不做」 | 任务暂时退出当天选择流程 |
| 标记今日大事 | 指定当前重要任务，遵守唯一性约束 |
| 开始专注 | 进入单任务执行情境 |
| 标记完成 | 更新任务完成状态并显示反馈 |
| 勾选每日基础事项 | 更新当天的基础事项状态 |
| 进入复盘 | 允许用户整理当日体验 |
| 生成明日候选 | 将建议交由用户确认或后续规划流程处理 |
| 发生日切 | 根据既定规则更新任务和每日基础事项状态 |

### 5.7 核心流程

**日常主流程：** 进入 Today → 逐项选择今日任务 → 进入 Focus → 开始当前行动 → 标记完成 → 进入 Review → 整理明日候选。

该流程不要求用户必须完成全部今日任务。用户可以跳过计时器，也可以不使用真实 AI 服务。

### 5.8 异常与边界状态

| 状态 | 设计要求 |
|---|---|
| 没有候选任务 | 明确告知当前状态，并提供可执行的下一步 |
| 没有今日任务 | 引导用户返回规划流程 |
| 没有完成任何任务 | 仍允许复盘，不使用失败提示 |
| 所有候选任务已处理 | 清楚说明下一步，不让用户误以为应用卡住 |
| AI 请求失败 | 提供非惩罚性错误反馈与可选重试 |
| 本地数据不可读取 | 告知错误，避免无提示地覆盖已有数据 |
| 导入备份失败 | 提供错误说明，不应破坏原有可用数据 |
| 任务发生跨日状态变化 | 确保状态与界面说明一致 |

## 06 / MVP 功能范围与实现状态

### 6.1 状态定义

- **已实现并可体验：** 公开 Demo 中可直接完成主要操作。
- **代码已实现，待验证：** 已存在相关代码或接口，尚需真实环境测试。
- **部分实现：** 已有基础能力，存在适配、语言或交互细节限制。
- **未实现 / 规划中：** 尚未开发或尚未纳入当前版本。

### 6.2 当前功能范围

| 功能 | 当前状态 | 备注 |
|---|---|---|
| Today / Focus / Review 页面 | 已实现并可体验 | 核心信息架构 |
| 逐张任务选择与等效按钮 | 已实现并可体验 | 边界状态仍需完善 |
| 每日基础事项（Daily Basics） | 已实现并可体验 | 清单持久，勾选状态每日重置 |
| 今日大事（One Big Thing） | 已实现并可体验 | 唯一性规则：标记新的自动取消旧的 |
| 可选计时器 | 已实现并可体验 | 15/25/45 分钟及自定义 |
| 行动步骤（添加 / 编辑 / 删除） | 部分实现 | 快速添加后自动生成默认步骤，编辑入口待补（测试发现 P05） |
| 对话式复盘 | 已实现并可体验 | 公开 Demo 使用模拟 AI 回复 |
| AI 生成明日候选的模拟交互 | 已实现并可体验 | 不代表真实模型已上线 |

| 屏幕阅读器支持 | 待完善 | 需要语义与状态反馈检查 |

### 6.3 MVP 的最小闭环

用户能够选择当天准备做的任务，进入专注流程，标记至少一项任务完成，并进行一次简短复盘。真实 AI 不应是完成这条流程的必要条件。

### 6.4 明确不纳入当前 MVP 的功能

详见 §3.7 产品非目标。这些是当前产品策略上的排除，不只是开发资源有限导致的延后。

## 07 / AI 功能与服务边界

### 7.1 AI 在产品中的角色

AI 是 Anew 的可选辅助能力，用于帮助用户整理自然语言表达、在复盘过程中提供温和的对话反馈、将反思内容转化为下一天的候选任务。AI 不应替代用户决定任务优先级，也不应将其建议包装为必须执行的安排。

### 7.2 公开 Demo：模拟模式

公开 Demo 使用预设模拟回复，展示 AI 功能对应的交互流程（用户输入 → 回复展示 → 任务建议衔接）。不调用真实模型、不产生费用、回复内容不代表实时理解用户输入。应在适当位置清楚说明当前回复为模拟性质。

### 7.3 真实 AI 服务的代码基础

项目已建立 `/api/ai-plan` 与 `/api/review-chat` 接口，包含模拟（Mock）、OpenAI 和 Anthropic 适配能力。代码为真实模型接入提供基础，但需完成服务配置、调用测试、部署检查及错误处理验证。

### 7.4 AI 输出原则

- 建议应具体、可行动，不制造过多新的选择。
- 语气应平和，避免责备和效率评价。
- 不应将用户未完成任务解释为失败。
- 应允许用户忽略或修改 AI 建议。
- 输出应尽可能符合当前界面的语言设置。
- 不应声称理解或诊断用户的心理健康状况。

### 7.5 失败与降级策略

- 清晰的加载与错误状态。
- 不暴露密钥或内部错误信息。
- 提供适当的重试方式。
- 不因请求失败丢失用户输入。
- 用户仍可继续完成非 AI 的主要操作。
- 不应将模拟回复静默伪装成真实模型调用结果。

### 7.6 安全与配置要求

- API 密钥只保存在服务端安全配置中。
- 不在前端代码中暴露服务端密钥。
- 真实 AI 接口应具有合理的访问控制和费用保护措施。
- 启用真实服务前需检查第三方模型的数据处理规则。

## 08 / 数据存储、隐私与兼容性

### 8.1 数据本地优先

Anew 以浏览器 localStorage 作为主要的用户数据存储方式。用户无需注册账号即可开始使用。本地存储降低首次使用门槛，也避免默认将个人任务内容集中上传至服务器。

### 8.2 当前数据管理能力

本地数据持久化、JSON 数据导出、JSON 数据导入、数据重置、对旧版存储键及旧版导出格式的兼容处理。

### 8.3 本地存储的局限

localStorage 不等同于永久、安全或跨设备的数据备份。以下情况可能造成数据丢失：用户清除浏览器站点数据、更换设备或浏览器、使用无痕浏览环境。因此 JSON 导出与导入是重要的自主备份方式。

### 8.4 AI 请求中的数据边界

在当前模拟模式下，AI 交互不调用第三方模型。启用真实 AI 服务后，用户主动触发 AI 功能时，必要的任务或复盘上下文会通过服务端接口发送至所配置的模型服务。实际发送哪些字段以最终接口实现为准。在真实模式上线前，需确认哪些内容会发送给 AI 服务、是否存在服务端请求日志、第三方模型服务如何处理提交的数据。

### 8.5 隐私与产品分析之间的取舍

Anew 希望在保护用户隐私的同时验证产品是否真的降低任务启动负担。但数据本地优先意味着产品无法自然获得完整的跨用户行为分析数据。这一问题不应仅通过增加第三方埋点工具解决，而需要权衡研究价值、数据最小化、用户知情同意和实现成本。目前尚未确定正式的数据采集方案。

## 09 / 指标体系与验证计划

### 9.1 核心指标

| 指标 | 定义 | 主要验证内容 |
|---|---|---|
| 首次任务启动时间 | 从进入规划流程到开始第一项任务的时间 | 启动阻力是否降低 |
| 首次决策完成率 | 首次使用时完成至少一次任务选择的用户比例 | 交互是否容易理解 |
| 主观决策负担 | 用户对规划过程难易程度的主观评价 | 选择过程是否更轻松 |
| 当日核心闭环率 | 完成选择、至少一项任务以及复盘的用户比例 | 核心流程是否连贯 |
| **跳过任务后续完成率** | **被跳过的任务在预设观察期内最终完成的比例** | **跳过机制与后续行动的关系** |

这些指标属于验证设计，不代表已实施自动采集或获得实际结果。

### 9.2 核心指标优先级

**第一优先级：首次任务启动时间** — 直接对应核心问题。**第二优先级：主观决策负担** — 判断即使启动时间变化不明显，用户是否感到更轻松。**第三优先级：交互理解与错误操作** — 观察用户是否理解滑动方向、星标含义、跳过状态及任务恢复规则。

### 9.3 跳过机制的验证难题

「界面不展示跳过惩罚」与「研究需要追踪任务后续状态」之间存在设计张力。需要区分：界面层面不显示惩罚性计数，研究层面是否在用户知情同意下保留最小限度的状态信息用于判断跳过任务的后续结果。当前尚未确定最终方案。

### 9.4 数据采集方案比较

| 方案 | 优势 | 局限 |
|---|---|---|
| 纯本地统计 + 用户主动导出匿名摘要 | 符合本地优先原则，用户控制权高 | 样本偏差明显 |
| 默认关闭的可选匿名遥测 | 有机会获取更连续的使用指标 | 需明确同意机制与技术保障 |
| 仅开展定性研究 | 易于理解行为背后的原因 | 难以得出量化结论 |

当前倾向优先探索本地统计与用户主动提供研究数据的方式。

### 9.5 研究方法

**第一阶段：可用性测试** — 确认基本交互是否容易理解。重点观察滑动理解、跳过含义、星标理解、Review 与明日候选的关系。

**第二阶段：对照测试** — 使用相近任务内容，对比 Anew 渐进式选择与传统并列清单，比较首次任务启动时间和主观决策负担。

**第三阶段：中长期使用观察** — 关注持续使用意愿、跳过机制是否减少使用压力、跨日状态理解、复盘是否有助于下一次任务启动。

## 10 / MVP 验收与成功标准

### 10.1 功能验收标准

- 用户可以进入 Today 并进行任务选择。
- 任务加入今日计划后能进入后续执行流程。
- 用户可以进入 Focus 并专注当前任务。
- 用户能够标记任务完成。
- 用户能够进入 Review 并完成基本复盘。
- 核心流程不依赖真实 AI 服务。
- 公开 Demo 在模拟模式下不需要访客提供 API 密钥。
- 本地数据能够正常保存、导出、导入和重置。
- 历史备份格式的兼容性得到回归测试。
- 页面能够适配主要移动端视口。
- 用户能够理解关键操作及状态变化。

### 10.2 体验验收标准

用户应能够理解逐张任务选择的操作方式、Keep today 与 Not today 的结果、今日大事的含义；在没有今日任务时获得明确引导；在未完成任务时仍能继续使用和复盘。同时应逐步满足文字对比度、键盘可达性、状态反馈及动画降级等无障碍要求。

### 10.3 成功的定义

Anew 的成功不应单纯等同于用户记录更多任务或达到更高完成率。更重要的是：**用户是否能够在不增加额外心理负担的情况下，更容易决定下一步并开始行动。**

## 11 / 当前局限与下一阶段路线

### 11.1 当前局限

- **产品体验尚不完整：** 缺少首次使用引导，部分空状态与过渡反馈需完善。
- **部分交互不够直观：** 滑动操作、跳过后去向、今日大事标记可能存在理解障碍。
- **视觉与无障碍细节待完善：** 部分浅色文字对比度不足，主题间存在细节不一致，动效缺少降级适配。
- **真实 AI 尚未完成公开部署验证：** 代码已具备接入基础，但真实模型集成测试仍需完成。
- **产品价值尚未充分验证：** 尚无量化证据证明渐进式选择优于传统清单。

### 11.2 近期：完善首次体验与界面细节

- 增加简短、可跳过的欢迎引导，让新用户快速理解产品并开始第一次任务选择。
- 优化滑动提示、跳过任务的状态说明、「今日大事」标记及每日基础事项的解释。
- 调整「快速添加」的默认步骤逻辑，允许用户自行添加、编辑或跳过。
- 完善空状态、过渡反馈、中文界面与六套主题的一致性，持续优化文字对比度和无障碍体验。
- 明确标注 AI Demo 的模拟性质，避免用户误以为回复来自真实模型。

### 11.3 中期：完善核心功能与使用体验

- 接入并测试真实 AI 服务，结合用户的复盘内容生成建议，并提供更自然的对话反馈。
- 探索 AI 辅助任务拆解，将复杂任务转化为 5 分钟内容易开始的具体行动，允许用户自由修改或采纳生成的步骤。
- 设计更温和的周度回顾，重点呈现已经完成的进展，而不是强调未完成任务或连续打卡。
- 改善数据备份与离线使用能力，提高长期使用的可靠性。

### 11.4 长期：验证产品价值与扩展方向

- 扩大真实用户测试规模。
- 与传统待办清单进行对照研究。
- 评估任务启动时间、主观决策负担及长期使用体验。
- 探索隐私保护下的匿名反馈与研究数据采集。
- 根据真实使用需求评估账号同步。
- 谨慎探索个性化能力，避免增加新的决策负担。

### 11.5 尚待决策的问题

| 开放问题 | 当前考虑 |
|---|---|
| 是否提供完整任务浏览入口？ | 可能提高查找效率，但可能削弱渐进式选择原则 |
| 如何更清晰地解释「今天不做」？ | 需要降低状态不确定性，同时避免失败感 |
| 是否记录跳过任务的历史状态？ | 需要权衡研究价值、隐私与数据复杂度 |
| 是否接入账号同步？ | 需要真实用户需求支持，不作为当前默认能力 |
| 如何处理 AI 建议的确认与编辑？ | 用户应保留控制权，不让 AI 自动增加管理负担 |
| 是否增加精力状态推荐？ | 可能提高适配程度，也可能增加开始前的判断步骤 |

## 12 / 项目总结

Anew 从任务启动困难这一具体问题出发，尝试重新组织传统待办工具的使用流程。项目不以功能丰富程度为主要目标，而是通过减少并列选择、突出当前行动、允许无惩罚性的跳过以及提供轻量复盘，探索更低负担的每日计划体验。

从产品定义、信息架构、核心交互到可运行 MVP，Anew 已形成相对完整的设计与实现框架。但它仍然是一项需要继续验证的产品探索。真实 AI 服务的集成效果、关键任务状态的可理解性、无障碍体验及长期产品价值，都有进一步研究与完善的空间。

**Anew 的目标不是让每一天都更高效，而是让开始一件事变得更容易。**
